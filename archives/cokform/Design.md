# Cokform Design System

> 만드는 사람·응답하는 사람·운영하는 사람의 흐름을 끊지 않는 UI 기준

이 문서는 Cokform의 브랜드와 제품 디자인을 함께 설명하는 정본이다. PDF 디자인 가이드의 내용을 유지하면서, 실제 화면을 만들거나 포트폴리오에서 프로젝트를 설명할 때 필요한 판단 기준을 한곳에 모은다.

---

## 1. 디자인 방향

Cokform은 한국 실무 환경에서 빠르게 만들고, 정확히 묻고, 응답을 잃지 않고, 다음 운영으로 넘어가도록 돕는 폼 서비스다. 따라서 장식보다 질문과 상태를 우선한다.

| 원칙 | 화면에서의 의미 |
|---|---|
| 질문이 먼저 | 제목·설명·필수 여부·입력을 장식보다 먼저 보여준다. |
| 한 화면 한 행동 | 대표 CTA 하나를 정하고 보조 행동은 시각적 무게를 낮춘다. |
| 상태는 즉시 | 저장됨·오류·마감·복구 상태를 짧은 문장과 아이콘으로 표시한다. |
| 되돌릴 수 있게 | 삭제·초기화·마감에는 확인과 복구 경로를 둔다. |
| 조건은 조용하게 | 조건부 질문은 필요한 순간에만 나타내고 다른 분기 질문을 섞지 않는다. |
| 모바일 우선 | 390px에서 가로 스크롤 없이 읽고 입력할 수 있어야 한다. |
| 개인정보는 명확하게 | 수집 목적·항목·보유 기간·동의·책임 주체를 폼 안에서 확인하게 한다. |

AI가 만든 듯한 균일한 카드, 과한 그림자, 동일한 스트로크의 반복, 장식적인 숫자 폰트, 불필요한 세미볼드, 의미 없는 hover 효과는 사용하지 않는다. 모든 시각 요소는 정보 구조나 다음 행동을 도와야 한다.

## 2. 브랜드 시스템

### 2.1 이름과 슬로건

- 국문: 콕폼
- 영문: Cokform
- 슬로건: 원하는 대로, 콕 묻고 받아요.
- 보조 설명: 한국 실무 흐름에 맞춘 개인정보 보호형 폼 빌더

“콕”은 귀여운 장식이 아니라 필요한 지점을 정확히 집는다는 의미다. 카피는 친근하되 유아적이지 않게, 신뢰감은 주되 법적·보안상 검증되지 않은 절대 표현은 피한다.

### 2.2 말투

권장 문장은 짧고 다음 행동이 보여야 한다.

- 필요한 질문만 추가하세요.
- 방금 저장됐어요.
- 이전 작성 내용을 복구했어요.
- 현재 응답을 받지 않습니다.
- 수집 목적과 보유 기간을 확인하세요.
- 다시 시도하거나 저장된 초안을 복구하세요.

피해야 할 문장:

- 100% 안전합니다.
- 해킹이 불가능합니다.
- 법적 책임이 전혀 없습니다.
- AI가 모든 응답을 완벽하게 처리합니다.

### 2.3 로고 사용

기본 로고는 웹 헤더·문서·소개 자료에, 심볼은 파비콘·앱 아이콘·좁은 영역에 사용한다. 로고 높이의 0.5배 이상을 최소 여백으로 두며 원본 비율을 유지한다.

금지 사항:

- 가로·세로로 늘리기
- 회전·기울이기
- 임의 색상·그라데이션·외곽선 적용
- 로고에 임의 그림자 추가
- 사진 위에 직접 배치
- 워드마크 일부를 잘라 심볼처럼 사용
- 제휴·공식 승인·보증을 암시하는 조합

권장 형식은 웹 원본 SVG, 인쇄 PDF, 투명 PNG, 일반 문서용 JPG다.

## 3. 색상 토큰

색상은 의미 토큰으로 사용한다. 새 색상을 추가하기 전에 기존 토큰으로 표현할 수 있는지 먼저 확인한다.

| 토큰 | HEX | 용도 |
|---|---|---|
| Ink | `#17251F` | 본문, 핵심 제목, 강한 텍스트 |
| Deep Green | `#0F5B46` | 주요 버튼, 강한 상태, 어두운 브랜드 면 |
| Cokform Green | `#17866D` | 링크, 선택, 상호작용 |
| Leaf Green | `#73B99D` | 보조 선, 그래픽, 약한 강조 |
| Soft Mint | `#D8F5E8` | 선택됨, 성공, 보조 배경 |
| Warm White | `#FFFDF8` | 카드, 문서, 밝은 표면 |
| Canvas | `#F5F3EC` | 앱 전체 배경 |
| Lime | `#D8ED59` | 히어로 포인트, 짧은 강조 |
| Error | `#B94A48` | 오류, 삭제, 위험 안내 |

`Cokform Green`과 `Warm White`의 대비는 작은 본문에 충분하지 않을 수 있다. 작은 흰 글자 버튼·본문·링크에는 `Deep Green` 또는 더 어두운 토큰을 사용한다. 색상만으로 상태를 구분하지 말고 문구·아이콘·위치를 함께 사용한다.

## 4. 타이포그래피

기본 글꼴은 **Pretendard**로 통일한다. 숫자·응답 건수·페이지 번호에 별도 장식용 숫자 폰트를 적용하지 않는다.

| 역할 | 기준 | 용도 |
|---|---|---|
| Display | Pretendard Bold, 짧은 행, 강한 대비 | 랜딩 히어로, 핵심 선언 |
| H1/H2 | Bold 또는 Semibold | 화면·섹션 제목 |
| H3/Label | Semibold 또는 Medium | 카드·문항·필드 라벨 |
| Body | Regular, 16px 기준 | 설명·질문·응답 |
| Caption | Regular, 12–13px | 날짜·보조 상태·힌트 |
| Number | Regular 또는 Medium | 건수·페이지·선택값 |

불필요한 세미볼드와 미디엄을 줄인다. 제목·라벨·본문 사이에 명확한 위계가 있을 때만 굵기를 바꾼다. 줄바꿈은 의미 단위가 유지되도록 하며, 긴 한국어 문장을 억지로 한 줄에 고정하지 않는다.

## 5. 간격·모서리·표면

기본 간격은 4px 단위를 사용하고 주요 여백은 8·12·16·24·32px에서 선택한다. 한 화면에서 서로 다른 radius를 세 종류 이상 섞지 않는다.

카드는 기본적으로 1px 경계와 평면 표면을 사용한다. 기본 그림자는 사용하지 않거나 `ELEV1` 하나만 사용한다. 드롭다운·모달처럼 콘텐츠가 실제로 떠야 할 때만 `ELEV2` 이상을 허용한다.

카드마다 다른 그림자·테두리 두께·모서리를 적용하지 않는다. 카드 안에 카드를 반복하는 구조는 설정 선택이나 단계 구분처럼 정보 계층이 필요한 경우에만 사용한다.

## 6. 컴포넌트

### 6.1 버튼

버튼 문구는 동작과 결과를 함께 말한다. `저장`, `제출`, `폼 만들기`, `응답 보기`, `이전 버전 복원`처럼 사용자가 결과를 예측할 수 있어야 한다.

| 종류 | 시각 규칙 | 사용 상황 |
|---|---|---|
| Primary | Deep Green 배경, 흰 글자 | 화면 대표 행동 |
| Secondary | Warm White 또는 투명, 경계 | 보조·취소·이전 |
| Tertiary | 배경 없음, 텍스트 링크 | 저강도 탐색 |
| Destructive | Error 토큰, 명확한 확인 | 삭제·영구 초기화 |
| Success | Mint 배경, Deep Green 글자 | 저장됨·복구됨 |

hover에서 버튼의 위치나 크기를 바꾸지 않는다. 색상·그림자·outline만 바꿔 포인터가 덜덜 떨리는 느낌을 막는다. 아이콘만 있는 버튼에는 `aria-label`과 툴팁을 제공한다. 모바일 터치 영역은 충분히 넓게 확보하고 서로 붙이지 않는다.

### 6.2 카드

카드는 정보를 그룹화할 때만 사용한다. 제목, 짧은 설명, 대표 행동 순서를 유지한다. 클릭하지 않는 카드에는 hover 효과를 넣지 않는다. 모든 카드의 스트로크 두께와 표면 대비를 일관되게 유지하되, 선택·오류·성공 상태는 테두리·아이콘·텍스트로 구분한다.

### 6.3 입력·질문

입력 순서는 질문 제목, 필수 여부, 설명·조건, 입력 영역이다. placeholder에 질문 자체나 필수 안내를 넣지 않는다. 오류 문구는 필드 아래에 원인과 해결 방법을 함께 표시한다.

긴 서술형 질문은 textarea를 사용하고 줄바꿈을 보존한다. 리치 텍스트는 편집기·저장 데이터·미리보기·응답 화면에서 같은 줄바꿈 규칙을 사용한다. 필수 문항은 시각적 표시와 `aria-required="true"`를 함께 제공한다.

### 6.4 상태·알림

| 상태 | 권장 문구 | 사용자가 할 일 |
|---|---|---|
| 저장 중 | 저장하는 중입니다 | 잠시 기다림 |
| 저장됨 | 방금 저장됨 | 계속 작성 |
| 초안 복구 | 이전 작성 내용을 복구했습니다 | 이어쓰기 또는 삭제 |
| 마감 | 현재 응답을 받지 않습니다 | 작성자에게 문의 |
| 오류 | 저장하지 못했습니다 | 다시 시도·복구 |
| 보안 확인 | 안전한 응답 제출을 확인하는 중입니다 | 잠시 기다림 |

중요한 오류를 토스트 하나로만 전달하지 않는다. 페이지 안에 `aria-live="polite"` 영역 또는 지속되는 오류 영역을 둔다.

## 7. 화면별 규칙

### 7.1 폼 편집기

폼 구조, 현재 질문, 가까운 추가 행동을 명확하게 나눈다. 질문 제목을 클릭하면 즉시 편집할 수 있지만 포커스를 갑자기 훔치지 않는다. 저장 중에도 입력을 막지 않는다. 새로고침 후 마지막 유효 버전과 복구 가능한 초안을 보여준다.

질문 추가·설명 추가·섹션 추가를 작은 버튼 하나에만 의존하지 않는다. 현재 질문 옆의 빠른 추가, 상단의 추가 메뉴, 키보드 Tab 순서를 함께 제공한다. 삭제는 즉시 파괴하지 말고 undo 또는 휴지통으로 되돌릴 수 있게 한다.

### 7.2 응답자 화면

공개 응답 화면임을 방해 없이 이해할 수 있어야 한다. 제목, 설명, 개인정보 수집 안내, 이메일 기록 여부, 질문 순서가 자연스럽게 이어진다. 운영자 메뉴와 작성자 권한을 노출하지 않는다.

새로고침·탭 전환·일시적 네트워크 끊김을 고려해 폼별·브라우저별 초안을 보존한다. 복구 사실과 초안 삭제 방법을 안내한다. 조건부 질문이 나타나면 보이지 않는 질문의 값이 제출되지 않는지 확인한다.

### 7.3 운영 화면

응답은 질문별 데이터가 아니라 한 명의 제출 맥락이 유지되는 한 덩어리로 보여준다. 검색·상태 필터·개별 삭제·전체 삭제는 같은 응답 목록 안에서 작동한다. 삭제 후에는 즉시 피드백과 복구 경로를 보여준다.

운영자는 수집 목적, 응답 기간, 필수 항목, 금칙어, 내보내기 범위를 확인할 수 있어야 한다. 응답 원문을 보는 권한은 작성자와 명시된 운영 권한으로 제한한다.

## 8. 반응형·접근성

| 구간 | 기준 |
|---|---|
| 0–479px | 단일 열, 카드 패딩 16px, 제목은 2–3줄 허용 |
| 480–767px | 단일 열 중심, 보조 정보만 2열 허용 |
| 768–1023px | 편집기·문서는 2열 검토, 입력 폭 우선 |
| 1024px 이상 | 콘텐츠 최대 폭 제한, 주변 여백으로 호흡 확보 |

페이지 전체에 가로 스크롤이 생기면 실패다. 긴 표·코드·다운로드 옵션만 컨테이너 내부에서 가로 스크롤한다. 일반 텍스트 대비는 4.5:1 이상, 큰 텍스트는 3:1 이상을 목표로 한다. 키보드 순서는 시각적 순서와 일치해야 하며 포커스 링을 제거하지 않는다. 오류는 색상 외에 문구와 위치로 전달하고 `prefers-reduced-motion`을 존중한다.

색맹 사용자를 위해 질문 유형을 컬러바 하나로만 구분하지 않는다. 아이콘, 텍스트 라벨, 형태 차이를 함께 제공한다.

## 9. 동작·데이터 UX 기준

- 자동 저장은 마지막 유효 상태를 유지하고 저장 중 입력을 막지 않는다.
- 새로고침 후 편집 중인 폼과 응답 초안을 복구한다.
- 탭 이동 후 돌아와도 편집값이 사라지지 않는다.
- Enter 줄바꿈은 저장·미리보기·응답 화면에서 동일하게 보인다.
- 조건부 질문은 선택값에 맞는 질문만 보이고 제출 데이터에서도 숨겨진 질문을 제거한다.
- 삭제는 휴지통 또는 undo로 복구할 수 있다.
- 버전 복원 전 현재 버전을 자동으로 보존한다.
- 오류는 원인과 다음 행동을 함께 제시한다.
- 버튼을 누른 뒤 다른 영역을 누르면 열린 메뉴·팝오버가 자연스럽게 닫힌다.
- 포인터 이동 때문에 버튼 위치가 흔들리거나 크기가 변하지 않는다.
- 검색 결과는 내가 만든 폼과 참여한 폼을 명확히 구분한다.
- 질문별 통계만 따로 떼어 응답자의 전체 맥락을 잃게 하지 않는다.

## 10. 배포 전 QA 체크리스트

### 편집자

- 질문 제목 수정
- 질문·설명·섹션 추가
- Enter 줄바꿈
- 필수 여부 변경
- 조건부 질문 구성
- 삭제·undo·휴지통
- 새로고침 후 복구
- 이전 버전 복원
- 모바일 390px 편집

### 응답자

- 공개 링크 접근
- 모바일 입력
- 조건부 질문 표시
- 숨겨진 질문 값 제거
- 개인정보 고지 확인
- 이메일 기록 여부 표시
- 최소 글자 수·금칙어
- 제출 완료 및 바로가기
- 새로고침 후 초안 복구
- 마감 상태 안내

## 11. 디자인 변경 규칙

Cokform을 다시 개발할 때는 이 문서의 토큰과 의미를 우선 사용한다. 새 기능을 넣기 전에 실제 사용자 문제, 성공 기준, 데이터 책임, 복구 경로를 기록한다. 구글폼·네이버폼과 비슷한 기능을 추가하더라도 그대로 복제하지 않고 한국 실무 흐름과 Cokform의 자유도·명확함·복구 가능성에 맞춰 판단한다.

새로운 카드, 그림자, 색상, 폰트, 애니메이션은 반드시 다음 질문을 통과해야 한다.

1. 사용자의 다음 행동을 더 명확하게 만드는가?
2. 모바일에서 입력을 방해하지 않는가?
3. 접근성과 대비를 해치지 않는가?
4. 저장·복구·오류 상태를 설명하는가?
5. 기존 토큰으로 표현할 수 없는 정말 새로운 의미인가?

통과하지 못하면 추가하지 않는다.
